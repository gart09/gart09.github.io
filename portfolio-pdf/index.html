검증 실행 공통 인터페이스

검증을 실행하는 곳에서는 Runner에 다음 3가지 인자만 전달하면 검증을 실행할 수 있는 구조로 구현

checks
실제로 검증할 정합성 검증 객체
ex) Stock, Structural, StateMachine...
scope
검증을 실행할 범위를 결정하는 매개변수
ex) 특정 쿠폰 이벤트, 시간 구간, 전체
triggerType
검증 실행 방식을 결정하는 매개변수
ex) 스케줄러, 수동 실행, 복구 후 재검증

Spring Batch 기반 비동기 검증

  • ALL 스코프는 한 번에 수백만 건을 검사하므로 시간이 많이 소요
    요청과 검증 실행을 분리하고 Spring Batch Job으로 처리하도록 구현
  • 마찬가지로 ConsistencyVerificationRunner를 통해 인자만 건네면 쉽게 실행
  • ConsistencyBatchJobFactory가 요청받은 검증 1개당 Step 1개씩 동적으로 조립해 Job을 구성

Step 구성 요소

01EventIdPageReader

  • event_id 기준 keyset pagination으로 coupon_event를 10개씩 조회
  • ItemStream으로 마지막 event_id를 저장해, 비정상 종료 후 재시작 시 해당 지점부터 이어서 읽음

02ConsistencyCheckItemProcessor

  • Reader가 읽은 페이지(coupon_event 10개)로 해당 Step의 검증을 실행
  • 실행 도중 오류가 발생하면 커밋된 페이지 이후부터 재실행

03CheckResultAccumulatorWriter

  • 페이지별 위반 건을 즉시 저장, 위반 건수는 Step 종료까지 누적
  • ItemStream으로 누적 위반 건수도 보존해 재시작 후에도 이전 집계 유지
  • Step 종료 시 StepCompletionListener가 VerificationResult를 최종 저장

위반 건수가 많아지면 검증 결과 저장이 통째로 실패

대량의 위반 데이터를 하나의 컬럼에 저장하며 발생한 MySQL 정렬 메모리 오류

문제 상황

  • VerificationResult의 diff_detail 컬럼 안에 위반 내역 메타데이터를
    하나의 sample 키로 저장
  • 위반 건수가 많아지면 컬럼 데이터가 커질 수 있음을 사전에 인지
    하지만 대량 위반은 발생하지 않을 것이라 판단, 기존 구조를 유지
  • 테스트 중 Redis와 로컬 환경의 시계가 어긋나면서 정상 데이터가 대량 위반으로 판정되어, 위반 1만 건이 한 번에 쌓이는 상황 발생
  • MySQL 조회 과정에서 대용량 diff_detail 값이 정렬 대상에 포함
    정렬 메모리가 부족해져 Out of sort memory 오류 발생

해결

  • 위반 사항을 verification_violation 테이블에 저장
    위반 1건을 행 1개로 분리
  • diff_detail은 각 검증이 필요한 개별 메타데이터만 저장하도록 역할을 축소
  • 위반 건수가 늘어나더라도 검증 결과 저장이 실패하지 않도록 개선
    유형·대상별 조회 및 복구 정책 연결이 가능해짐

배운 점

  • 문제 가능성을 인지했지만, 발생 가능성이 낮다고 판단해 구조 개선을 후순위로 미룸
  • 가장 큰 문제는 실제 이슈 발생 시 어떤 영향으로 이어질지 충분히 검토하지 않았다는 점
  • 당시 MySQL에 대한 이해가 부족해, 정렬 과정에서 큰 컬럼으로 인해 오류가 발생할 수 있다는 점을 고려하지 못함
  • 이슈의 발생 가능성뿐 아니라 발생 시 영향까지 확인한 후, 문제의 크기를 판단해 구조 변경 여부를 논의하는 것이 중요함을 깨달음

로컬 Git Hook으로 커밋 메시지 컨벤션 검증

일관된 Git 히스토리를 만들기 위해 커밋 시점의 규칙 검증을 도입

도입 배경

  • 이전 프로젝트에서 팀원마다 커밋 방식이 달랐음
    메시지의 일관성이 떨어져 커밋 히스토리를 관리하는 데 불편함을 겪음
  • 커밋 컨벤션을 문서화하는 것만으로는 일관성을 유지하기 어렵다고 판단
    문서화에 그치지 않고 커밋 단계에서 규칙을 검증할 필요성을 느낌

구현 방법

  • 커밋 메시지 컨벤션을 .git/hooks 아래의 commit-msg 파일로 검증하도록 구현
  • 하지만 .git은 저장소 메타데이터 폴더
    git 버전 관리 대상이 아니므로, Hook 스크립트를 커밋해 팀원과 공유할 수 없었음
  • gitHooks 폴더에 commit-msg를 두고, 프로젝트 실행 시 해당 파일을 .git/hooks/로 복사하는 Gradle Task를 구현

[문제] 로컬 Git Hook은 강제력이 부족

  • 저장소를 새로 받은 팀원이 프로젝트를 실행해야만 로컬 Git Hook이 설치됨
    팀원이 프로젝트를 한 번도 실행하지 않으면 검증이 동작하지 않음
  • git commit --no-verify로 Git Hook을 무시할 수 있음
    컨벤션을 지키지 않아도 커밋 가능
  • PR이 원격 저장소에서 머지될 때는 로컬 Git Hook이 동작하지 않음
  • 결과적으로 PR 머지 시점에는 커밋 메시지가 다시 일관성 없이 남게 됨

개선 방향

  • 로컬이 아닌 원격 저장소에서 규칙을 검증하도록 GitHub Actions를 도입
  • PR 생성·업데이트 시 커밋 메시지 컨벤션을 검사
    검증을 통과한 PR만 머지되도록 구성
  • 현재 진행 중인 프로젝트에도 적용
    일관된 커밋 메시지가 유지되도록 강제할 수 있었음

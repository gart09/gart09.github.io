검증 실행 공통 인터페이스

검증을 실행하는 곳에서는 Runner에 다음 3가지 인자만 전달하면 검증을 실행할 수 있는 구조로 구현

checks
실제로 검증할 정합성 검증 객체
ex) Stock, Structural, StateMachine...
scope
검증을 실행할 범위를 결정하는 매개변수
ex) 특정 쿠폰 이벤트, 시간 구간, 전체
triggerType
검증 실행 방식을 결정하는 매개변수
ex) 스케쥴러, 수동 실행, 복구 후 재검증

Spring Batch 기반 비동기 검증

  • ALL 스코프는 한 번에 수백만 건을 검사하므로 시간이 많이 소요
    동기 처리 대신 Spring Batch로 비동기 처리하도록 구현
  • 마찬가지로 ConsistencyVerificationRunner를 통해 인자만 건네면 쉽게 실행
  • ConsistencyBatchJobFactory가 요청받은 검증 1개당 Step 1개씩 동적으로 조립해 Job을 구성

Step 구성 요소

01EventIdPageReader

  • event_id 기준 keyset pagination으로 10개 이벤트 데이터를 하나의 청크로 처리
  • ItemStream으로 마지막 event_id를 저장해, 비정상 종료 후 재시작 시 해당 지점부터 이어서 읽음

02ConsistencyCheckItemProcessor

  • Reader가 읽은 페이지(event 10개)로 해당 Step의 검증을 실행
  • 실행 도중 오류가 발생하면 커밋된 페이지 이후부터 재실행

03CheckResultAccumulatorWriter

  • 페이지별 위반 건을 즉시 저장, 위반 건수는 Step 종료까지 누적
  • ItemStream으로 누적 위반 건수도 보존해 재시작 후에도 이전 집계 유지
  • Step 종료 시 StepCompletionListener가 VerificationResult를 최종 저장

정합성 검증 복구 정책

복구 실행부터 이력 저장 · 재검증까지의 공통 파이프라인

  • 정합성 검증마다 위반 규칙과 복구 방식은 상이
    하지만 복구를 실행하고 결과를 관리하는 흐름은 공통으로 필요
  • 복구 정책 파이프라인은 일관되게 실행
    검증별 실제 복구 로직은 각 팀원이 ConsistencyRecoveryPolicy로 구현
  • 복구 정책 실행 · 복구 이력 저장 · 성공 시 재검증 ·
    VerificationResult 상태 갱신 흐름을 공통화

복구 실행 공통 인터페이스

트리거 종류(관리자 실행, 자동 실행)에 상관없이 ConsistencyRecoveryDispatcher.recover() 하나를 거쳐 복구하도록 구현

resultId
복구 대상인 FAIL 상태의 정합성 검증 결과
FAIL 상태가 아니면 즉시 예외로 거부
action
관리자가 선택한 복구 방식(RecoveryAction)
검증별 정책에 맞는 실제 복구 로직을 선택

복구 진행 과정

01정책 실행

  • 위반 verificationResult의 checkName으로 수행한 검증 식별
  • 하나의 검증에서 여러 coupon_event가 개별적으로 위반될 수 있음
  • 해당 검증의 복구 정책을 찾아 각 위반 건에 대한 복구 수행
  • 건별 복구 결과를 List<RecoveryOutcome>로 반환

02이력 저장

  • ConsistencyRecoveryDispatcher가 List<RecoveryOutcome>를 순회
  • 각 RecoveryOutcome의 복구 성공·실패 여부와 관계없이 모든 복구 시도를 recovery_result 테이블에 저장
  • 건별 REQUIRES_NEW 트랜잭션으로 결과를 즉시 커밋해 이력을 보존

03재검증 및 상태 갱신

  • 복구 성공 시 동일한 검증을 자동으로 다시 실행
  • 재검증까지 통과한 경우에만 최종 복구 성공으로 인정하고 상태를 갱신

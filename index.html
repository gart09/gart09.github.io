UBot · 문제해결과정 1

채팅 RAG 파이프라인: 답변 문장 필터

로컬 LLM 환경에서 검색된 FAQ의 답변 전체가 아니라 질문과 유사한 문장만 LLM에 전달하도록 파이프라인을 설계

문제 상황

  • 선택된 FAQ의 답변을 모두 LLM에 전달할 경우, 질문과 무관한 내용까지 함께 전달되는 문제
    • 예) "휴대폰 요금제는 중간에 바꿔도 되나요?"에 Top-k(검색 결과 상위 k개 FAQ) FAQ의 답변이 모두 전달됨
      • FAQ 1: 요금제를 바꿔도 결합 할인은 유지됩니다. 요금제 변경은 월 1회 가능합니다.
      • FAQ 2: 번호이동과 기기 변경을 함께 진행할 수 있습니다.
      • FAQ 3: 단말 교체와 선택약정은 별개라 약정을 유지한 채 기기를 바꿀 수 있습니다. 새 단말 할부금은 따로 청구됩니다.
      • LLM 답변: 휴대폰 요금제를 중간에 바꾸는 것은 가능하지만, 월 1회만 가능합니다. 또한, 요금제 변경 시 결합 할인은 유지됩니다. 다만, 요금제 변경이 약정 기간 중이라면 기기 변경과는 별개로 이루어져야 하며, 새 단말의 할부금은 별도로 청구됩니다.
        → Top-k FAQ의 답변 전체가 전달되어, 질문과 무관한 새 단말 할부금 내용까지 답변에 포함됨

해결 과정

  • 선택된 FAQ의 답변을 모두 LLM에 전달할 경우, 질문과 무관한 내용까지 함께 전달되는 문제
    • 원인
      • FAQ 선택은 FAQ 질문 단위로 하는데, LLM에 넘기는 입력은 답변 전체라서 단위가 맞지 않음
    • 해결
      • 답변을 문장으로 나누고 사용자 질문과 다시 비교해, 관련 있는 문장만 전달
      • LLM 없이 문장 부호로 나누는 BreakIterator(JDK 기본 문장 분리기) 사용. 목록은 별도 규칙으로 보완
        • 목록은 항목 단위로 묶어 비교, 들여쓴 줄은 직전 항목의 이어지는 내용으로 처리
        • 안내 문장과 목록 사이에 빈 줄이 있어도 한 묶음으로 처리
        • "1.5GB"처럼 숫자 뒤에 공백 없이 이어지는 값은 목록으로 보지 않는 예외 처리

결과

  • LLM 호출을 사용하지 않고, LLM에 FAQ 답변 전체가 아닌 질문과 유사한 문장만 전달

실시간 FAQ 검색어 랭킹

사용자 질문의 RAG 검색 결과에 많이 포함된 FAQ를 인기, 급상승 랭킹으로 제공

문제 상황

  • 유저들의 질문을 랭킹화하기
  • 다중 인스턴스 상황에서의 랭킹 집계 문제
  • 랭킹 순위 조작

해결 과정

  • 유저들의 질문을 랭킹화하기
    • 원인
      • 유저 질문은 표현과 세부 정보가 제각각이라, 내용과 답변을 가공하는 과정에서 LLM이 빈번하게 호출되 자원을 크게 소모
    • 해결
      • 질문 검색에 사용된 FAQ의 정보들로 랭킹을 구성
      • 실제 인기 질문을 대표하진 못하지만, 원하는 FAQ가 있는 유저의 요구를 간접적으로 충족
  • 다중 인스턴스 상황에서의 랭킹 집계 문제
    • 원인
      • 개발 당시에는 단일 인스턴스였으나 다중 인스턴스로 확장될 가능성이 있어, 서버에 저장하면 인스턴스마다 결과가 달라질 수 있음
    • 해결
      • 스케줄러가 1분마다 랭킹을 한 번에 계산해 Redis에 Top 5 스냅샷으로 저장. 엔드포인트는 Redis의 값만 조회
      • 스케줄러에 ShedLock을 적용해 여러 인스턴스에서 동시에 실행되는 것을 방지
  • 랭킹 순위 조작
    • 원인
      • 검색 횟수가 적은 FAQ의 비율이 튀는 현상
      • 같은 사용자의 반복 질문
      • 랭킹에 노출된 FAQ만 계속 선택되는 자기강화
    • 해결
      • 현재 윈도우의 최소 검색 횟수와 기준 기간의 최소 표본 수를 지정해, 건수가 아주 작은 경우 배제
      • 질문을 정규화해 테이블에 저장. 랭킹 집계 윈도우안에 같은 정규화 질문이 테이블에 존재하면 랭킹에서 제외
      • 랭킹의 FAQ를 선택해 답변을 얻는 경우 FAQ 사용 기록 테이블에 추가하지 않고, DB의 FAQ 답변을 바로 프론트에 전달

결과

  • API는 Redis만 조회. 프론트는 GET /rankings 한 번으로 인기, 급상승 정보를 모두 조회 가능
  • 모든 인스턴스가 같은 랭킹 공유

FAQ 모니터링: 개선이 필요한 FAQ 탐지

로그 지표로 개선이 필요한 FAQ를 목록화하고, 관리자가 확인해 개선할 수 있는 FAQ 품질 관리 대시보드

문제 상황

  • 수정 후 한 번도 검색되지 않은 FAQ가 "사용량 낮음"으로 잡히지 않는 현상
  • AI 검토 결과의 판단과 근거가 일관되지 않는 현상

해결 과정

  • 수정 후 한 번도 검색되지 않은 FAQ가 "사용량 낮음"으로 잡히지 않는 현상
    • 원인
      • 수정 전 로그를 빼려고 "수정 후 로그만" 조회했는데, 수정 후 로그가 없는 FAQ는 조회 결과에서 아예 사라짐
      • 조건을 아예 없애면 수정 전 로그까지 세게 되어, 이미 고친 FAQ가 계속 목록에 등장
    • 해결
      • FAQ를 먼저 가져오고, 그 FAQ에 수정 후 로그를 LEFT JOIN으로 합치는 방식으로 변경
      • 수정 후 사용 로그가 없는 FAQ도 0건으로 남아 "사용량 낮음"으로 판정됨
  • AI 검토 결과의 판단과 근거가 일관되지 않는 현상
    • 원인
      • AI가 자유롭게 서술하는 응답을 받아, 판단 결과와 조치 권고가 서로 어긋날 수 있고 형식도 응답마다 달라질 수 있는 구조
    • 해결
      • 프롬프트에 판단 기준(중복, 구분 필요, 중복 아님, 근거 부족)을 명시하고 판단별 조치 규칙을 강제
      • AI가 자유롭게 문장을 쓰지 않고 정해진 JSON 양식으로만 답하게 하고 서버가 해당 JSON을 검증

결과

  • SQL 쿼리 한 번으로 개선 유형 판정, 제외 적용, 정렬, 페이지네이션을 수행
  • 판단 근거와 판단 결과의 일치는 프롬프트 규칙으로 유도
  • AI 검토 응답의 형식 오류는 JSON 스키마와 서버 검증으로 차단

정합성 검증 과정에 Spring Batch 도입

대량 데이터 검증을 요청과 분리해 비동기로 처리하고, 실패 시 중단 지점부터 재개할 수 있는 구조로 설계

문제 상황

  • 대량(300만건 가량)의 데이터 정합성 검증이 오래 걸려, 요청이 끝날 때까지 대기하는 문제
    • 데이터 정합성 검증: 선착순 쿠폰 발급 후 DB와 Redis의 데이터가 서로 맞는지 사후에 검사하는 기능
      (예: 재고 수량 일치, Redis와 DB 간 데이터 유실, 쿠폰 상태 전이 오류)
  • 검증 도중 오류가 발생하면 처음부터 다시 실행해야 하는 문제

해결 과정

  • 대량(300만건 가량)의 데이터 정합성 검증이 오래 걸려, 요청이 끝날 때까지 대기하는 문제
    • 원인
      • 검증 요청과 검증 실행이 한 흐름에 묶여 있어, 실행이 끝날 때까지 요청이 대기해야 함
    • 해결
      • 요청과 검증 실행을 분리하고 Spring Batch를 사용한 Job으로 처리
      • BatchJobFactory가 요청받은 검증 1개당 1개의 Step으로 동적으로 조립해 Job을 구성
  • 검증 도중 오류가 발생하면 처음부터 다시 실행해야 하는 문제
    • 원인
      • 수백만 건을 한 번에 읽고 처리하는 과정 중간에 실패했을 때 처음부터 다시 시작해야 함
    • 해결
      • Spring Batch Step의 Reader, Processor, Writer가 각자 진행 지점을 저장하도록 구성해, 실패 시 중단된 지점부터 재시작
        • EventIdPageReader (읽기)
          • 검증 대상인 coupon_event(쿠폰 발급 기록 테이블)를 청크 단위로 조회
          • ItemStream으로 검증을 진행한 마지막 coupon_event_id를 저장해, 재시작 시 해당 지점부터 이어서 읽음
        • ConsistencyCheckItemProcessor (검증)
          • Reader가 읽은 페이지 단위로 검증을 실행
          • 오류가 발생하면 커밋된 페이지 이후부터 재실행
        • CheckResultAccumulatorWriter (결과 누적 저장)
          • 페이지별 위반 건을 즉시 저장
          • 누적 위반 건수도 ItemStream으로 보존해, 재시작 후에도 이전 집계 유지

결과

  • 검증 요청과 실행이 분리되어, 수백만 건 검증도 Job으로 비동기 처리
  • 실패 시 처음부터가 아니라 중단된 지점부터 재개 가능

위반 건수가 많아지면 검증 결과 저장이 통째로 실패

대량의 위반 데이터를 하나의 컬럼에 저장하며 발생한 MySQL 정렬 메모리 오류

문제 상황

  • 위반 건수가 많아지면 검증 결과 저장이 통째로 실패하는 문제
    • 테스트 중 Redis와 로컬 환경의 시계가 어긋나면서 정상 데이터가 대량 위반으로 판정되어, 위반 1만 건이 한 번에 쌓이는 상황 발생
    • MySQL에서 Out of sort memory 오류가 발생해 검증 결과 저장이 실패

해결 과정

  • 위반 건수가 많아지면 검증 결과 저장이 통째로 실패하는 문제
    • 원인
      • VerificationResult(검증 결과 저장 테이블)의 diff_detail(위반 내역 컬럼) 안에 위반 내역 메타데이터를 모두 저장
      • 위반 건수가 많아지면 컬럼 데이터가 커질 수 있음을 사전에 인지했지만, 대량 위반은 발생하지 않을 것이라 판단해 기존 구조를 유지
      • MySQL 조회 과정에서 시계 오차로 인한 1만 건의 위반이 발생. diff_detail안의 대량의 데이터가 정렬 대상에 포함되어 정렬 메모리가 부족해짐
    • 해결
      • 위반 사항을 별도의 verification_violation 테이블에 저장. 위반 1건을 행 1개로 분리
      • diff_detail은 각 검증이 필요한 개별 메타데이터만 저장하도록 역할을 축소

결과

  • 위반 건수가 늘어나더라도 검증 결과 저장이 실패하지 않음
  • 유형, 대상별 위반 사항 조회가 가능해짐

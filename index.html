채팅 RAG 파이프라인: 답변 문장 필터

로컬 LLM 환경에서 추가 LLM 호출 없이, 검색된 FAQ의 답변 전체가 아니라 질문과 유사한 문장만 LLM에 전달하도록 파이프라인을 설계

구현 목표

  • 로컬 LLM 환경에서 추가 LLM 호출 없이 질문과 무관한 정보가 LLM 입력에 섞이는 현상 방지
  • 응답속도 및 소모 자원 감소를 위해 LLM 호출을 최대한 하지 않는 방향으로 구현

문제 상황

  • 선택된 FAQ의 답변을 모두 LLM에 전달할 경우, 질문과 무관한 내용까지 함께 전달되는 문제
    • 예) "휴대폰 요금제는 중간에 바꿔도 되나요?"에 Top-k(검색 결과 상위 k개 FAQ) FAQ의 답변이 모두 전달됨
      • FAQ 1: 요금제를 바꿔도 결합 할인은 유지됩니다. 요금제 변경은 월 1회 가능합니다.
      • FAQ 2: 번호이동과 기기 변경을 함께 진행할 수 있습니다.
      • FAQ 3: 단말 교체와 선택약정은 별개라 약정을 유지한 채 기기를 바꿀 수 있습니다. 새 단말 할부금은 따로 청구됩니다.
      • LLM 답변: 휴대폰 요금제를 중간에 바꾸는 것은 가능하지만, 월 1회만 가능합니다. 또한, 요금제 변경 시 결합 할인은 유지됩니다. 다만, 요금제 변경이 약정 기간 중이라면 기기 변경과는 별개로 이루어져야 하며, 새 단말의 할부금은 별도로 청구됩니다.
        → Top-k FAQ의 답변 전체가 전달되어, 질문과 무관한 새 단말 할부금 내용까지 답변에 포함됨

해결 과정

01비교 단위 결정

원인
FAQ 선택은 FAQ 질문 단위로 하는데, LLM에 넘기는 입력은 답변 전체라서 단위가 맞지 않음
고민
질문 단위로 고른 FAQ의 답변에서 질문과 관련 없는 부분을 걸러낼 로직이 필요하다고 판단
해결
답변을 문장으로 나누고 사용자 질문과 다시 비교해, 관련 있는 문장만 전달

02문장 분리 방식 결정

쟁점
문장으로 나누려면 분리 기준이 필요
고민
  • LLM으로 문장을 추출하면 LLM 호출이 늘어 구현 목표와 충돌하므로 규칙 기반으로 분리하기로 판단
  • 다만 마침표 기준으로만 나누면 번호나 글머리 목록이 항목 중간에서 잘려 의미가 깨짐
구현
LLM 없이 문장 부호로 나누는 BreakIterator(JDK 기본 문장 분리기) 사용. 목록은 별도 규칙으로 보완
  • 목록은 항목 단위로 묶어 비교, 들여쓴 줄은 직전 항목의 이어지는 내용으로 처리
  • 안내 문장과 목록 사이에 빈 줄이 있어도 한 묶음으로 처리
  • "1.5GB"처럼 숫자 뒤에 공백 없이 이어지는 값은 목록으로 보지 않는 예외 처리

결과

  • LLM 호출을 사용하지 않고, LLM에 FAQ 답변 전체가 아닌, 질문과 유사한 문장만 전달

한계

  • FAQ 질문 검색 기준 0.79, 답변 문장 비교 기준 0.49는 테스트 질문으로 여러 조합을 시도해 LLM JUDGE 정답률 지표가 가장 좋은 값으로 선정
    하지만 테스트 질문셋에 맞춘 값이므로 과적합 가능성 존재
  • 이후 FAQ와 파이프라인 변경으로 동일 조건 재현 불가
    문장 필터 적용 전후를 같은 조건으로 비교하지 못해 개선 정도를 수치로 확인하지 못함

구현 과정

01자주 묻는 질문의 정의

쟁점
자주 묻는 질문을 보여 주려면 무엇을 집계 단위로 삼을지 정해야 함
고민
  • 가장 좋은 방법은 실제 유저 질문을 클러스터링해 순위대로 보여 주는 것
  • 유저 질문은 표현과 세부 정보가 제각각이라 하나의 답변으로 묶어 보여 주기 어렵다고 판단
  • 묶은 질문의 내용과 답변을 가공하는 과정에서 LLM이 빈번하게 호출될 것으로 판단
  • 결론적으로 빠른 답변이라는 랭킹의 목적을 달성할 수 없다고 판단
구현
질문 검색에 사용된 FAQ의 순위와 해당 FAQ의 답변을 반환. 질문을 직접 묶지는 않지만, 원하는 FAQ가 있는 유저의 요구를 간접적으로 충족

02랭킹 반환 방식

쟁점
랭킹을 언제 집계하고 어디에 저장해 반환할지 정해야 함
고민
  • 랭킹은 1초, 0.1초 단위 갱신이 필요하지 않은 작업이므로, 요청마다 매번 집계할 필요가 없다고 판단
  • 개발 당시에는 단일 인스턴스였으나 다중 인스턴스로 확장될 가능성이 있어, 서버 메모리에 저장하면 인스턴스마다 결과가 달라질 수 있다고 판단
구현
  • 스케줄러가 1분마다 랭킹을 한 번에 계산해 Redis에 Top 5 스냅샷으로 저장. 엔드포인트는 Redis의 값만 조회
  • 스케줄러에 ShedLock을 적용해 여러 인스턴스에서 동시에 실행되는 것을 방지

03랭킹 순위 왜곡 처리 방식

검색 횟수가 적은 FAQ의 비율이 튀는 현상

원인
평소 1건이던 FAQ가 5건이 되면 5배지만 의미 있는 급상승은 아님
해결
현재 윈도우의 최소 검색 횟수와 기준 기간의 최소 표본 수를 지정해, 건수가 아주 작은 경우 배제

같은 사용자의 반복 질문

쟁점
한 사용자가 같은 질문을 반복해 의도적으로 FAQ 순위를 조작할 수 있음
고민
같은 FAQ가 선택됐다는 이유로 중복 처리하면 정상 질문까지 제외될 수 있음. 표현이 달라도 같은 FAQ가 Top-k로 선택될 수 있기 때문. 따라서 같은 사용자의 같은 질문만 집계에서 제외하도록 결정
구현
같은 질문으로 인한 왜곡을 막기 위해 질문을 정규화해 테이블에 저장. 랭킹 집계 윈도우(기본값 1시간) 안에 같은 정규화 질문과 같은 userId가 이미 있으면 랭킹에서 제외

랭킹에 노출된 FAQ만 선택되는 자기강화

원인
랭킹에 노출된 FAQ를 선택해 얻은 답변이 다시 사용 기록으로 쌓이면, 노출된 FAQ가 계속 상위에 남음
해결
랭킹의 FAQ를 선택해 답변을 얻는 경우 FAQ 사용 기록 테이블에 추가하지 않고, DB의 FAQ 답변을 바로 프론트에 전달

결과

  • 모든 인스턴스가 같은 랭킹 공유

한계

  • 임계값(최소 검색 횟수, 판정 배수 등)은 초기값이므로 실제 트래픽을 기준으로 한 조정 필요
  • 랭킹 도입 후 LLM 호출 감소량과 응답 시간 단축 효과는 정량 측정하지 못함

FAQ 모니터링: 개선이 필요한 FAQ 탐지

로그 지표로 개선이 필요한 FAQ를 목록화하고, 관리자가 확인해 개선할 수 있는 FAQ 품질 관리 대시보드

개요

  • FAQ의 현재 버전 사용 로그를 바탕으로 품질이 낮은 FAQ들을 목록화하고, 필요한 경우 관리자에게 조치 방법을 권유하는 기능
  • 개선 항목 유형
    • 검색 품질 낮음(LOW_RAG_QUALITY): 검색 평균 유사도가 낮은 FAQ
    • 중복 의심(DUPLICATE_SUSPECTED): FAQ 임베딩 유사도 검색 결과 1위로 선정됐는데, 2위 FAQ와 유사도 차이가 작은 경우가 빈번한 FAQ
    • 사용량 낮음(LOW_USAGE): 수정된 지 하루가 지나도 한 번도 검색되지 않은 FAQ

구현 목표

  • 1,000건 이상의 FAQ 중 개선 대상을 자동 탐지
  • AI 검토로 개선이 필요한 FAQ의 조치 권고와 판정 근거를 관리자 화면에서 제공

문제 상황

  • 수정 후 한 번도 검색되지 않은 FAQ가 "사용량 낮음"으로 잡히지 않는 현상
  • AI 검토 결과의 판단과 근거가 일관되지 않는 현상
  • 개선이 필요 없는 FAQ를 목록에서 없애는 기능이 없음

해결 과정

01수정 후 한 번도 검색되지 않은 FAQ가 "사용량 낮음"으로 잡히지 않는 현상

원인
  • 수정 전 로그를 빼려고 "수정 후 로그만" 조회했는데, 수정 후 로그가 없는 FAQ는 조회 결과에서 아예 사라짐
  • "사용 0건"이어야 잡히는 FAQ가 집계 대상에서 빠진 것
고민
  • 조건을 아예 없애면 수정 전 로그까지 세게 되어, 이미 고친 FAQ가 계속 목록에 등장
  • 수정 전 로그는 빼면서도, 로그가 없는 FAQ는 남겨야 했음
해결
  • FAQ를 먼저 가져오고, 그 FAQ에 수정 후 로그를 LEFT JOIN으로 합치는 방식으로 변경
  • 수정 후 사용 로그가 없는 FAQ도 0건으로 남아 "사용량 낮음"으로 판정됨

02AI 검토 결과의 판단과 근거가 일관되지 않는 현상

원인
AI가 자유롭게 서술하는 응답을 받아, 판단 결과와 조치 권고가 서로 어긋날 수 있고 형식도 응답마다 달라질 수 있는 구조
고민
  • 프롬프트 문장을 더 정교하게 다듬는 방법과 응답 구조를 강제하는 방법을 비교
  • 문장 지시는 모델이 어길 수 있고, 어겼는지 서버가 확인할 수단이 없다고 판단
  • 무엇을 판단할지(내용)는 프롬프트로 정하고, 어떤 모양으로 답할지(형식)는 서버 검증으로 보장하도록 역할을 나눔
해결
  • 내용
    • 프롬프트에 판정 기준(중복, 구분 필요, 중복 아님, 근거 부족)을 명시하고 판정별 조치 규칙을 강제
    • 판단 근거의 결론이 판단 결과와 같아야 한다는 규칙을 명시
  • 형식
    • AI가 자유롭게 문장을 쓰지 않고 정해진 JSON 양식으로만 답하게 함
    • 서버가 해당 JSON을 확인, 판정값이 올바른지 검증, 어긋나면 응답 거부

원인

고민
FAQ ID로만 제외하면 FAQ를 수정한 뒤에도 계속 숨겨질 수 있음. 제외 기록이 어느 시점의 FAQ에 대한 판단인지 구분할 기준이 필요하다고 판단
해결
제외 단위를 FAQ, 개선 유형, FAQ 버전으로 지정. FAQ를 수정하면 버전이 바뀌어 기존 제외가 적용되지 않으므로 별도 처리 없이 다시 평가

결과

  • SQL 쿼리 한 번으로 개선 유형 판정, 제외 적용, 정렬, 페이지네이션을 수행
  • 판단 근거와 판단 결과의 일치는 프롬프트 규칙으로 유도
  • AI 검토 응답의 형식 오류는 JSON 스키마와 서버 검증으로 차단

한계

  • 판정 기준값은 초기값이며 운영 데이터로 조정 필요
  • AI 검토 프롬프트 변경 효과와 판정 정확도는 정량 검증하지 못함

검증 실행 공통 인터페이스

검증을 실행하는 곳에서는 Runner에 다음 3가지 인자만 전달하면 검증을 실행할 수 있는 구조로 구현

checks
실제로 검증할 정합성 검증 객체
ex) Stock, Structural, StateMachine...
scope
검증을 실행할 범위를 결정하는 매개변수
ex) 특정 쿠폰 이벤트, 시간 구간, 전체
triggerType
검증 실행 방식을 결정하는 매개변수
ex) 스케줄러, 수동 실행, 복구 후 재검증

Spring Batch 기반 비동기 검증

  • ALL 스코프는 한 번에 수백만 건을 검사하므로 시간이 많이 소요
    요청과 검증 실행을 분리하고 Spring Batch Job으로 처리하도록 구현
  • 마찬가지로 ConsistencyVerificationRunner를 통해 인자만 건네면 쉽게 실행
  • ConsistencyBatchJobFactory가 요청받은 검증 1개당 Step 1개씩 동적으로 조립해 Job을 구성

Step 구성 요소

01EventIdPageReader

  • event_id 기준 keyset pagination으로 coupon_event를 10개씩 조회
  • ItemStream으로 마지막 event_id를 저장해, 비정상 종료 후 재시작 시 해당 지점부터 이어서 읽음

02ConsistencyCheckItemProcessor

  • Reader가 읽은 페이지(coupon_event 10개)로 해당 Step의 검증을 실행
  • 실행 도중 오류가 발생하면 커밋된 페이지 이후부터 재실행

03CheckResultAccumulatorWriter

  • 페이지별 위반 건을 즉시 저장, 위반 건수는 Step 종료까지 누적
  • ItemStream으로 누적 위반 건수도 보존해 재시작 후에도 이전 집계 유지
  • Step 종료 시 StepCompletionListener가 VerificationResult를 최종 저장

위반 건수가 많아지면 검증 결과 저장이 통째로 실패

대량의 위반 데이터를 하나의 컬럼에 저장하며 발생한 MySQL 정렬 메모리 오류

문제 상황

  • VerificationResult의 diff_detail 컬럼 안에 위반 내역 메타데이터를
    하나의 sample 키로 저장
  • 위반 건수가 많아지면 컬럼 데이터가 커질 수 있음을 사전에 인지
    하지만 대량 위반은 발생하지 않을 것이라 판단, 기존 구조를 유지
  • 테스트 중 Redis와 로컬 환경의 시계가 어긋나면서 정상 데이터가 대량 위반으로 판정되어, 위반 1만 건이 한 번에 쌓이는 상황 발생
  • MySQL 조회 과정에서 대용량 diff_detail 값이 정렬 대상에 포함
    정렬 메모리가 부족해져 Out of sort memory 오류 발생

해결

  • 위반 사항을 verification_violation 테이블에 저장
    위반 1건을 행 1개로 분리
  • diff_detail은 각 검증이 필요한 개별 메타데이터만 저장하도록 역할을 축소
  • 위반 건수가 늘어나더라도 검증 결과 저장이 실패하지 않도록 개선
    유형·대상별 조회 및 복구 정책 연결이 가능해짐

배운 점

  • 문제 가능성을 인지했지만, 발생 가능성이 낮다고 판단해 구조 개선을 후순위로 미룸
  • 가장 큰 문제는 실제 이슈 발생 시 어떤 영향으로 이어질지 충분히 검토하지 않았다는 점
  • 당시 MySQL에 대한 이해가 부족해, 정렬 과정에서 큰 컬럼으로 인해 오류가 발생할 수 있다는 점을 고려하지 못함
  • 이슈의 발생 가능성뿐 아니라 발생 시 영향까지 확인한 후, 문제의 크기를 판단해 구조 변경 여부를 논의하는 것이 중요함을 깨달음

정합성 검증 공통 인터페이스 / Spring Batch 기반 정합성 비동기 검증 파이프라인
  • 3명의 팀원이 정합성 검증 파트를 담당
  • 정합성 검증을 실행할 공통 로직의 필요성을 느끼고, 정합성 검증을 실행하고자 하는 곳에서 ConsistencyVerificationRunner를 통해 인자만 건네면 쉽게 실행할 수 있도록 구현
  • 팀원들이 본인이 담당한 검증의 로직 작성에만 신경쓸 수 있는 환경을 조성
  • 매개변수로 checks, scope, triggerType 3가지 타입을 넘겨받음
    • checks
      • 실제 검증하고자 하는 정합성 검증 객체
      • 어떤 검증이 추가될지 모르기 때문에, List<ConsistencyCheck> 형식으로 모든 검증을 처리할 수 있도록 구현
      • 원하는 코드에서 A, B 두 개의 검증을 실행하고 싶다면, checks.add(A, B)와 같이 직관적으로 작성할 수 있도록 함
    • scope
      • 검증을 실행할 범위를 결정하는 매개변수
      • EVENT: 특정 couponEvent의 항목들에 대해 검사
      • AS_OF_RANGE: 특정 시간 범위에 대한 항목들에 대해 검사
      • ALL: 모든 데이터에 대해서 검사. Batch 작업으로만 진행할 수 있음
    • triggerType
      • 어떻게 이 검증이 실행됐는지를 결정하는 매개변수
      • EVENT_TRIGGER: 특정 이벤트 발생 시(쿠폰 사용, 쿠폰 발급 마감 등)
      • SCHEDULED: 스케쥴러의 의한 주기 실행
      • ON_DEMAND: API를 통한 수동 실행
      • RECOVERY_REVERIFICATION: 복구 정책 실행 직후 정상복구됐는지 확인하기 위한 실행
  • ALL 스코프는 한 번에 수백만 건을 검사해야 해서, 동기 처리 대신 Spring Batch로 비동기 처리하도록 구현
  • 마찬가지로 <ConsistencyCheck>를 통해 인자만 건네면 쉽게 실행할 수 있도록 함
  • ConsistencyBatchJobFactory가 요청받은 검증(Check) 1개당 Step 1개씩 동적으로 조립해 Job을 구성
  • 한 Step이 배치 오류로 실패하면 비정상 작동이므로, 그 이후 Step들은 실행되지 않음
  • 하지만 한 Step 검증이 실패하면 정상 작동이므로, 그 이후 Step들은 실행됨
  • Step 하나는 다음 3가지 요소로 구성
    • EventIdPageReader
      • event_id 기준으로 keyset 페이징하며 10개 단위로 읽음
      • ItemStream을 구현해 마지막으로 읽은 event_id를 저장, Step이 재시작되면 이어서 읽음
    • ConsistencyCheckItemProcessor
      • Reader가 읽은 페이지(이벤트 10개)를 해당 Step의 검증기 하나로 실행
      • Chunk 크기는 1로 설정해, 페이지(이벤트 10개) 하나가 처리될 때마다 커밋되도록 함
      • 실행 도중 오류가 발생했다면, 커밋된 페이지 이후부터 실행하도록 함
    • CheckResultAccumulatorWriter
      • 페이지별 위반 건을 즉시 저장하고, 위반 건수는 Step이 끝날 때까지 누적
      • ItemStream을 구현해 누적된 위반 건수도 저장, Step이 재시작돼도 이전 페이지의 집계가 유지됨
      • Step이 끝나면 ConsistencyStepCompletionListener가 누적된 결과를 최종 VerificationResult로 확정 저장
  • 전체적인 검증 코드의 흐름은 다음과 같다.

정합성 검증 복구 정책
  • 정합성 검증과 마찬가지로, 모든 검증이 사용하는 공통 복구 정책 파이프라인의 필요성을 느껴 인터페이스로 구현
  • 검증마다 위반 항목이 다르므로, 검증별 복구 로직 자체는 각 팀원이 담당 검증에 맞춰 정책(ConsistencyRecoveryPolicy)으로 따로 구현
  • "복구 정책 실행 → 복구 이력 저장 → 복구 성공 처리 시 재검증 → 위반 VerificationResult 상태 갱신"으로 이어지는 흐름을 공통화해, 관리자 수동 실행과 시스템 자동 트리거가 트리거 종류와 무관하게 ConsistencyRecoveryDispatcher.recover() 하나만 거치도록 구현
  • 매개변수로 verificationResultId, action 두 가지를 넘겨받음
    • verificationResultId
      • 복구할 대상이 되는 FAIL 상태의 정합성 검증 결과
      • FAIL 상태가 아닌 결과에 복구를 요청하면 즉시 예외로 거부
    • action
      • 관리자가 화면에서 고른 복구 방식(RecoveryAction)
      • 검증마다 복구 방식이 다름 (재고 정합성 검증의 경우 재고 카운터 재계산, 초과발급 회수 두 가지 복구 정책이 존재)
      • 실제 복구 방식은 각 정책을 담당하는 팀원이 각자 구현
  • verificationResult의 checkName으로 해당 검증 정책을 찾아 복구를 진행하고, 복구 결과를 RecoveryOutcome 목록으로 반환
  • ConsistencyRecoveryDispatcher 이 목록을 순회하며 RecoveryOutcome 하나마다
    • 복구 성공/실패 상관 없이 recovery_result 테이블에 저장, 복구 시도 기록을 남기도록 함
    • 이때, 복구 건 1건마다 REQUIRES_NEW 트랜잭션으로 복구 결과가 기존 트랜잭션과 별개로 바로 커밋되도록 함
    • 복구 성공일 경우 같은 검증으로 재검증까지 자동 실행해, 실제로 복구가 됐는지 확인한 뒤에만 최종 성공으로 인정
  • 전체적인 복구 코드의 흐름은 다음과 같다.

개발 이슈
[문제] 위반 건수가 많아지면 검증 결과 저장이 통째로 실패함
  • 이전에는 VerificationResult 테이블 내부 컬럼 diff_detail에 위반 내역의 메타 데이터들을 하나의 sample키에 저장
    • 위반 건수가 무수히 많아진다면 한 컬럼의 데이터 크기가 너무 커질 수 있다는것을 팀 회의에서 인지
    • 하지만 위반 건수가 많이 안나올 것이고, 아직 발생하지 않은 문제를 미리 생각할 필요는 없다는 판단 하에 기존 구조를 유지했음
  • 이후 테스트 중 Redis와 로컬 환경의 시계가 어긋나며 정상 데이터가 대량으로 위반 판정되는 상황이 실제로 발생, 위반 1만 건이 한 번에 쌓이며 문제가 드러남
    • MySql이 자체적으로 테이블을 조회할 때 결과를 정렬하는 과정에서, diff_detail 값이 정렬용 메모리 버퍼에 올라감
    • 이때 한도 크기(256KB)를 초과하여 Out of sort memory 오류가 발생함
[해결방안]
  • 위반 사항을 하나의 JSON에 뭉쳐 담지 않고, verification_violation이라는 별도 테이블을 만들어 위반 1건을 행 1개로 분리
  • 기존 diffDetail은 각 검증마다 개별적으로 저장하고 싶은 메타데이터를 저장할 수 있도록 남김
  • 위반 건수가 늘어도 저장이 실패하지 않게 됐고, 유형·대상별로 위반을 조회하고 복구 정책과 짝지을 수 있게 됨
[배운점]
  • 문제가 발생할 수 있음을 인지했지만 아직 발생하지 않았고 구조상 많은 위반이 발생하지 않을 것임을 근거로 문제를 뒤로 넘긴게 발단
  • 가장 큰 문제는 해당 이슈가 발생했을 때 어떤 일이 일어날 것인가?에 대한 논의가 없었다는 점
  • 이 경우, 팀원들의 MySql에 대한 지식이 얕아 정렬이 발생할 때 한 컬럼의 크기가 큰 경우 오류가 발생한다는 사실을 몰랐음
  • 이후 개발에선, 어떤 이슈가 발생했을 때 그 이슈로 인해 어떤 문제가 발생하는지 실제로 찾아보고, 해당 문제의 대소여부를 판단해 구조 변경을 논의할 예정
